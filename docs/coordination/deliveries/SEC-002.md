## 1. Resumen de la Solución Implementada

Se corrigió la falta de aislamiento en `scripts/test_auth_suite.ts` que provocaba que la suite pudiera conectarse a PostgreSQL o leer/escribir sobre el archivo de base de datos local del proyecto (`data/gwen_db.json`) y heredar variables del entorno del proyecto.

### Principales Modificaciones en `scripts/test_auth_suite.ts`:

1. **Eliminación de Imports Estáticos y `dotenv` a Nivel Raíz:**
   - Se removió `import dotenv from 'dotenv'; dotenv.config();` del inicio del script para evitar la carga automática de credenciales y variables del archivo `.env` del proyecto.
   - Se removió el `import` estático de `src/server/db.js`, sustituyéndolo por una importación dinámica (`await import('../src/server/db.js')`) que se ejecuta estrictamente **después** de configurar el entorno de aislamiento.

2. **Configuración de Aislamiento Previo al Import:**
   - **Captura de Rutas Base:** Se capturó la ruta absoluta del repositorio (`repoRoot`) y el directorio de trabajo original (`originalCwd`) antes de cualquier cambio de entorno.
   - **Snapshot de Variables de Entorno:** Se guardó una copia de las variables relevantes (`DATABASE_URL`, `POSTGRES_URL`, `TEST_MEMORY_ONLY`, `NODE_ENV` y cualquier variante de `SUPERADMIN_BOOTSTRAP_*`).
   - **Neutralización de Conexiones a Base de Datos:** Se eliminaron `DATABASE_URL` y `POSTGRES_URL` del entorno para prevenir la inicialización de pools de PostgreSQL.
   - **Configuración de Variables de Test:** Se forzaron `TEST_MEMORY_ONLY = 'true'` y `NODE_ENV = 'test'`.
   - **Limpieza de Variables de Bootstrap:** Se eliminaron todas las variables `SUPERADMIN_BOOTSTRAP_*` heredadas antes de inicializar la base de datos.
   - **Directorio Temporal Aislado con `mkdtemp`:** Se creó un directorio temporal exclusivo mediante `fs.mkdtempSync(path.join(os.tmpdir(), 'gwen-auth-suite-'))` y se cambió el directorio de trabajo (`process.chdir(tempDir)`). Dado que `db.ts` resuelve `DATA_DIR` y `.env` a partir de `process.cwd()`, cualquier lectura o guardado del motor JSON fallback ocurre dentro del directorio temporal, evitando tocar `data/gwen_db.json` del proyecto.

3. **Lectura Estática Segura de `server.ts`:**
   - En las pruebas de verificación estática (tests 51 y 52), se sustituyeron las lecturas relativas `./server.ts` por la ruta absoluta `serverTsPath` (resuelta contra `repoRoot` antes del cambio de directorio).

4. **Garantía de Restauración y Limpieza en `finally`:**
   - Todo el flujo de prueba se ejecuta dentro de un bloque `try ... finally`.
   - En el bloque `finally`:
     - Se restaura el directorio de trabajo original (`process.chdir(originalCwd)`).
     - Se restauran las variables de entorno a su estado inicial.
     - Se realiza la eliminación segura (`fs.rmSync`) únicamente del directorio temporal propio validado dentro de `os.tmpdir()`.
   - No se invocan llamadas a `process.exit()` antes de la finalización del bloque `finally`.

5. **Preservación de Aserciones:**
   - Se mantuvieron intactas todas las aserciones, mensajes de verificación y nombres de los 52 casos de prueba de la suite sin alterar su lógica ni enmascarar posibles fallos.

## 2. Límites y Alcance

- **Alcance Específico:** Esta intervención protege y aísla exclusivamente la suite `scripts/test_auth_suite.ts`.
- **Límites:** No modifica de manera global el comportamiento de otras suites de test existentes en el repositorio ni altera la lógica de producción en `src/server/db.ts` ni en otros módulos de la aplicación.
